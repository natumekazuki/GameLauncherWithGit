# GameLauncherWithGit

## 開発・リリース運用

### 課題と対応予定

- 不具合、機能要求、対応が必要な後追いは [GitHub Issues](https://github.com/natumekazuki/GameLauncherWithGit/issues) で管理し、重複は既存の Issue に集約する。着手順は依頼内容と影響を踏まえ、データの安全性や主要な同期動作に関わるものを優先する。
- 正式版ごとに `vX.Y.Z` の Milestone を使い、対応予定が決まった Issue を割り当てる。Milestone 未指定は対応版未定のバックログとする。追加・延期するときは対象 Issue の割り当てと理由を更新する。
- 変更は作業ブランチで進め、`main` に統合する。対応した Issue は対象の変更が `main` に反映され、必要な確認が完了してから閉じる。重複や不採用の場合は理由を残して閉じる。Issue の完了と正式公開は別であり、Milestone は対象版の公開後、未完了課題の延期または対象外を整理して閉じる。
- リリース範囲を決めるときと公開前に、対象 Milestone の未完了課題と、Milestone 未指定でも今回の変更に関連する課題を確認する。未完了の非ブロッカーは公開判断と分け、延期する理由と引継ぎ先を Issue に残す。

### 互換性とデータ保護

実際に利用中の環境では、ゲーム登録・関連リポジトリ・セーブリンクの情報を含む `game-library.db`、`settings.json`、サムネイル、ゲームのセーブデータ、関連リポジトリのデータと同期先、および適用済みのデータ移行を維持対象とする。アプリ更新後も登録情報と設定を利用でき、セーブデータや同期先を損なわないようにする。必要な移行を行う場合も、既存データとその意味を維持する。

利用・適用済みかどうかで維持対象を判断し、Git タグの有無だけでは判断しない。未配布の開発途中の仕様や画面配置そのものとの互換性は保証しないが、そこで実際に使われているデータは保護する。データの消失や利用不能を伴う変更は、メジャーバージョンを上げるだけで実施せず、影響と対応方法を示して承認を得る。

### バージョン

正式版は `X.Y.Z` 形式とし、複数の種類の変更を含む場合は影響が最も大きいものに合わせる。

- `X`（メジャー）: 既存の動作環境、利用中の機能またはデータとの互換性を壊す変更。`Y` と `Z` を `0` に戻す。
- `Y`（マイナー）: 互換性を保つ機能追加や、機能・操作性の改善（不具合修正を除く）。`Z` を `0` に戻す。
- `Z`（パッチ）: 互換性を保つ不具合修正や、機能を追加しない内部改善・依存更新・文書変更。

番号の更新対象と Windows のビルド・MSIX 確認は、[バージョン更新チェックリスト](docs/design/windows-msix-keyvault-signing.md#7-バージョン更新チェックリスト)に従う。

### 正式公開

1. 公開範囲を決め、作業ブランチで対象版の番号を更新する。`docs/releases/vX.Y.Z.md` には変更内容と互換性・移行・利用・安全への影響を記録する。詳細文書やソースへのリンクは、その版の内容に対応するコミットの完全ハッシュで固定する。
2. 公開対象の変更を `main` に統合し、対象コミットで必要なビルド・動作確認を行う。MSIX を配布する場合は配布用パッケージも確認する。実施結果と未確認範囲はリリースノートと分けて公開判断時の確認記録に残し、最終的な公開対象のコミットと配布物に対応することを確かめる。
3. 公開対象の `main` のコミットに `vX.Y.Z` タグを付け、同じタグを指定して GitHub Release を作成する。公開済みタグは移動・削除しない。同名タグのローカルとリモートが食い違う場合は強制更新せず、原因と対応を確認する。

方針の定義は、Issue や Milestone の更新、push、統合、タグ操作、公開の実行許可を代替しない。

### プレビュー公開

- 正式版に向けた確認用として、作業ブランチの確定コミットに `vX.Y.Z-preview.N`（`N` は1から増加）のタグを付け、同じタグで GitHub Release を Prerelease・非Latestとして公開する。プレビュー公開のための `main` 統合は行わず、正式公開時は上記の手順に従う。
- 番号更新と対象コミット・配布物の確認は正式版と同様に行う。`docs/releases/vX.Y.Z-preview.N.md` には変更内容と互換性・移行・利用・安全への影響を記録し、利用に影響する既知の制限を明示する。検証結果・未確認範囲は確認記録、後追い課題は Issue で扱う。プレビューでも利用中のデータは保護する。
- アプリの表示番号は数値の `X.Y.Z`、サイドロード MSIX は `X.Y.Z.B` とし、`B` は `ApplicationVersion` に合わせる。各公開で `ApplicationVersion` を増やし、同じ `X.Y.Z` のプレビューから正式版へ移る際も末尾を `0` に戻さない。公開済みタグ・パッケージは差し替えず、修正は新しい番号で出す。
- MSIX とともに、サブモジュール・ネイティブ依存・ライセンス・ビルド手順を含む対応ソース一式を配布する。GitHub 自動生成のソースZIPだけではサブモジュールの内容を含まないため代用しない。公開操作には対象と範囲への明示承認が必要。

## Windows での UI 確認

Windows、.NET 9 の MAUI 開発環境、Git 2.38.0 以降が必要です。初回はサブモジュールも取得します。

シナリオ抽出のnative buildにはVisual Studio 2022のC++ x86/x64ツール、C++ ATL、Windows SDK、CMakeが必要です。スクリプトはATLを含むVisual Studioインスタンスを選び、32/64bitのHost・Hook・注入helperを構築します。初回はCMake依存取得にもネットワークを使います。

```powershell
git submodule update --init --recursive
./scripts/build-luna-native.ps1
dotnet build src/GameLauncherWithGit/GameLauncherWithGit.csproj -f net9.0-windows10.0.19041.0
$env:GAMELAUNCHER_DATA_DIRECTORY = Join-Path ([System.IO.Path]::GetTempPath()) ("GameLauncherWithGit-ui-" + [guid]::NewGuid().ToString("N"))
$env:WEBVIEW2_USER_DATA_FOLDER = Join-Path $env:GAMELAUNCHER_DATA_DIRECTORY "webview2"
dotnet run --project src/GameLauncherWithGit/GameLauncherWithGit.csproj -f net9.0-windows10.0.19041.0 --no-build
```

`GAMELAUNCHER_DATA_DIRECTORY` に絶対パスを指定すると、DB・設定・サムネイル・ログの保存先をそのディレクトリへ切り替えます。指定が不正な場合は起動に失敗し、通常の保存先へは戻りません。既存データのコピーや移行は行いません。上の例は毎回空の検証用ディレクトリを使い、WebView2 のデータも分離します。検証プロセスは設定したシェルから起動してください。このモードでは通常起動の単一起動制御を使わないため、同じ検証ディレクトリで複数起動しないでください。

未指定時は従来の保存先を使い、起動時に登録済みリポジトリを監視・同期します。検証用ディレクトリへ実データを持ち込まず、実際のセーブデータやリモートを登録しないでください。Windows の自動起動設定はプロファイル分離の対象外なので、検証中は変更しないでください。

「ゲーム追加」でタイトルだけを入力して保存すると、リポジトリや実行ファイルを使わず一覧の表示を確認できます。「設定」やゲーム編集、通知などの画面を確認できます。自動確認には、合成データと非表示の描画経路を使ってください。画像を共有する前に、パスや個人情報が含まれていないことを確認してください。

PC・記録Webの画面を変更するときは、[製品UIの設計方針](docs/design/maui-blazor-architecture.md#2-設計方針)に従い、通常時の表示と、操作結果の前後で既存のボタン・入力・本文の位置が変わらないことを実描画で確認します。

## ゲーム設定とGit状態

ゲームの表紙またはタイトルを選ぶと作品の詳細が開きます。選択だけでは起動せず、詳細の「起動する」またはカード左下の起動ボタンで起動します。シナリオは詳細の「シナリオを見る」から開きます。カード右下でピン留めを切り替えます。「ゲーム設定」から実行ファイルや関連リポジトリなどを変更できます。関連リポジトリを設定済みの作品では、「Git状態を更新」でそのリポジトリの状態だけを読み直します。同じリポジトリを使う別の作品にも結果が反映されます。この操作では fetch・pull・コミット・プッシュを行いません。

「ローカル先行」「リモート先行」は手元に保持している追跡ブランチとの比較です。実際の送信先での受領確認とは異なります。

同期が停止した作品では、競合などの原因を解消してから「同期を再開」を選びます。これはゲームの起動や、詳細でのGit状態の読み直しとは別の操作です。

関連リポジトリのブランチは、作品詳細の「ブランチ操作（即時反映）」から切り替えます。切り替えはゲーム設定の「保存」を待たず、ゲーム設定の変更を破棄しても元には戻りません。

### 自動コミットと自動プッシュの間隔

「設定」→「同期」で、自動コミットと自動プッシュの間隔を別々に指定できます（各0〜1440分、全ゲーム共通）。たとえば2分と15分に設定すると、変更をこまめにローカルへコミットし、未送信のコミットはまとめて送れます。0は無効ではなく、その処理に追加の待ち時間を設けない設定です。両方が0（旧設定で項目がない場合を含む）なら従来どおり動作します。

間隔はリポジトリごとに、最初の未処理の変更・未送信のコミットからそれぞれ数えます。後から変更がなくても期限に処理し、後続の変更で期限を延ばしません。「変更検知の待機」や失敗後の再試行とは別です。トレイの「すべて同期」や、競合解消後の「同期を再開」は間隔を待ちません。コミット済みでも未送信なら同期完了ではありません。

間隔を設定した同期の送信対象は現在のブランチです。送信先を一つに特定できなければ、プッシュせず通知に理由を示します。別のブランチに切り替えても元の未送信コミットは残り、元のブランチに戻ると再び確認します。
HTTP(S) で認証が必要な場合は、URLに認証情報を含めず Git Credential Helper などを使ってください。

## シナリオ抽出

ゲーム編集で次回起動からのON/OFFを設定します（初期値ON）。抽出設定の「画面から選択」を押して3秒以内にゲームを前面にするか、ウィンドウ・プロセスの検索で対象を選び、確認してテスト接続します。取得元ごとの直近の文章を比較し、本文・名前などの用途を指定します。名前の取得元から届く内容を話者に使うため、キャラクター名の事前登録は不要です。文章検索・表示の一時停止を使い、「判定」で分類と話者の仕上がりを確認できます。「確定して記録」で候補と本体パスをゲーム別に記憶し、その後の本文から保存します。テスト受信分は保存しません。接続後も選び直し・再試行できます。本のアイコンからシナリオ画面を開き、ゲーム単位の本文・分類・話者を閲覧・修正できます。分類はセリフ・地の文・未判定です。プレイ中は「区間を開始」→「末尾を固定」の順に操作し、名前を付けて区間を保存します。本文の両端を指定して区間を保存することもできます。区間外の本文も残り、ゲーム全体/区間/分類で絞ったTXTを全件出力できます。登録削除後も履歴と区間は残ります。

保存履歴では名前・本文それぞれの部分一致と分類・区間を組み合わせ、すべての条件に一致する本文を閲覧・TXT出力できます。名前・本文は検索ボタンまたはEnterで適用し、空欄は条件にしません。本文行を開くと、画像、話者・分類の訂正、原文・分割、一括操作の対象選択に進めます。その本文を含む保存済み区間があれば、詳細から該当区間を選んで名前とタグを編集できます。一括修正と選択した原文の削除は「その他」から行います。削除前に、同じ受信原文から分割された本文も含めて影響を確認できます。「履歴管理」では区間の改名・削除と、抽出設定を残すゲーム単位の全履歴消去を行えます。区間だけを削除しても本文は残ります。本文・全履歴の削除は取得停止後に確定し、元に戻せません。

区間には自由な名前のタグを任意で複数付けられます。区間作成時、本文の詳細、または PC の「履歴管理」で編集し、同じゲームの既存タグも再利用できます。TXT・ZIPの出力画面で、指定タグの区間だけを含める条件と、指定タグの区間を除外する条件を選べます。複数タグはいずれかに一致する区間が対象で、重なる部分は除外を優先します。重複区間の本文は二重出力せず、タグ未指定なら現在の区間・分類・名前・本文の条件で出力します。

取得はベストエフォートで、OCR・翻訳・全作品対応・欠落救済は提供しません。信頼できるゲームだけへ接続してください。動作・データ・安全境界の詳細は[シナリオ抽出設計](docs/design/scenario-extraction.md)、依存と配布条件は[Third-party notices](THIRD-PARTY-NOTICES.md)を参照してください。

関連リポジトリを設定した作品では、本文・訂正・画像・区間・経路などの記録が、リポジトリと Git ブランチごとに切り替わります。新しい枝には記録がなく、元の枝に戻ると保存済みの記録へ戻ります。抽出設定やタグ名の定義は作品で共通です。枝の出典がない記録は「通常の記録」と表示します。PC で別の枝を開いても書き込み先は変わらず、「閲覧中」と「記録先」を区別して表示します。

正式記録中はゲームを最前面にし、`Alt+Shift+S`でタイトルバーと枠を除いたスクリーンショットを保存できます。シナリオ画面の「その他」→「撮影設定」でキーと撮影ウィンドウを変更できます。Ctrlはゲームのスキップ操作と重なることがあるため、ゲームや他アプリで使わない組合せを選んでください。撮影対象は本文の取得先から自動選択し、別ウィンドウを選んでも本文の取得先は変わりません。画像は撮影時に最後に受け付けた本文へ紐づき、該当の本文行を開いて確認できます。厳密な行同期ではなく、その付近のシーンとして利用します。

撮影キーの変更に失敗した場合は以前の有効なキーへ復旧します。復旧できない場合は未登録として再設定を案内します。撮影失敗や処理中の拒否は、ゲームのフォーカスを変えずWindows通知と短い音で知らせます（連続通知は5秒間抑制、Windows側の通知・音設定にも依存）。直近の失敗は記録停止後もアプリ起動中は撮影設定で確認できます。タイトルがない窓も候補に表示します。通常終了は受付済み撮影を待ち、10秒の猶予後は中止を要求し、処理と保存境界が確定してから終了します。

シナリオ画面の「その他」→「書き出し」で、現在の区間・分類・名前・本文の条件に一致する資料を本文TXT・構造情報ZIP・完全版ZIPから選んで出力できます。初期選択の構造情報ZIPには`manifest.json`と`material.json`だけを含み、本文・画像本体は含めません。完全版は`texts.jsonl`と`images/`のPNGも含み、同じ画像は1ファイルにまとめます。manifestには区間の名前・元境界・タグと収録本文との対応を含み、無絞込みのゲーム全体ZIPから全保存区間を利用できます。絞込み時は収録本文と交わる区間だけを含めます。外部解析用のschemaと位置の照合方法は[ZIP契約](docs/design/scenario-extraction.md#手動スクリーンショットと分析用zip)を参照してください。画像はPNGで保存し、本文の削除時は他の本文から使われていない画像だけを削除します。ゲーム登録を削除しても履歴と画像は残ります。

同じ作品の連続する本文は保存後に別処理で照合します。タグや区間指定は不要で、原文・各周回の順番・分岐の一言・その回だけの画像は残ります。`material.json`では照合済みの共通本文を一度だけ読み、出現参照から各回の順序を復元できます。選択外の初出本文や画像は混ぜません。訂正・再分割・削除時は古い照合を失効させ、未処理がある出力は`matchingComplete=false`で区別します。完全版ZIPの`texts.jsonl`は出現ごとの本文をそのまま保持します。共通読取APIはZIPと[二権限のシナリオMCP](#シナリオ-mcp)で使用します。

フローチャートアイコンで、未タグ・区間未設定も含めたゲーム全体の観測経路を表示できます。照合済みの共通本文と分岐・合流をまとめ、出現を選ぶとフローの詳細でその回の画像を見られます。「本文・画像へ」からは本文の詳細へ戻れます。取得中の経路区切りは次の本文から、履歴の「ここから別経路」はその出現の直前だけの接続を切り、他周回の接続は残します。本文の両端指定から、範囲を本編と接続しない独立フローチャートへ分けることもできます。本文一覧の区間・分類・検索はフローチャートには適用しません。

既存の手動場面・関連区間・タグ・接続先は、PCでは「その他」→「保存済みの手動場面」、記録Webでは「区間」→「保存済みの手動場面」から参照できます。手動作図は行わず、名前やタグは区間で編集します。手動場面や接続は観測経路とは別に保存され、元の本文・画像は複製されません。区間と場面は作品タグを共有し、全履歴を消去しても手動場面・接続・作品タグは保持されます。

取得中の一時停止は、ゲーム編集の次回起動ON/OFFや取得元一覧の表示停止とは別です。停止中の本文・名前・撮影要求は保存せず、再開時にも取り込みません。停止前の受付済み処理は元の本文へ保存し、再開後は最初の新しい本文から別経路にします。新しい本文が来るまでは撮影できません。ZIPの`manifest.screenshotOccurrences`からは、本文ファイルやPNGを開かずに、選択された各原文の画像IDを引けます。添付なしの空配列と選択外の項目不在は区別します。

履歴一覧の画像ボタンには原文に紐づく枚数を表示します。0枚の本文はボタンを無効にし、件数取得失敗は0枚と区別します。本文の削除が確定した後に画像の後片付けだけが失敗した場合、一覧を更新したうえで未回収件数を示します。「履歴管理」の「不要画像の後片付けを再試行」で、すべてのゲームの未参照画像を整理できます。失敗した画像情報は保持され、参照中の画像は削除しません。

保存処理と分類のtestは実ユーザーDBを使わず実行できます。

```powershell
dotnet test tests/GameLauncherWithGit.Capture.Tests
```

## プレイ中の記録をブラウザーで操作する（Windows）

Windows アプリの「設定」→「記録Web」で待受状態と [localhost URL](http://localhost:47832/) を確認し、「コピー」または「開く」で同じ PC のブラウザーから利用できます。待受はループバック限定で、アプリ起動時に開始し、トレイ常駐中は継続し、アプリ終了時に閉じます。起動に失敗しても PC アプリは利用でき、設定の「記録Web」に理由と対処を表示します。

Web は PC のプレイ対象と現在の Git ブランチに追従します。プレイ対象は PC でのゲーム起動、または稼働中のゲームの記録を PC で確定すると決まります。すでに起動しているゲームを記録するには、PC のシナリオ画面で作品を開き、記録バーの「記録の準備」から接続して「確定して記録」を押します。履歴の表示、準備、テスト接続だけでは Web の対象は変わりません。ゲームを終了すると Web は待機します。記録だけを終了した場合、ゲームが動いている間は同じ作品を表示します。

対象がない間は待機し、Web から別の作品を選ぶことはできません。PC と Web で記録開始・一時停止・再開・終了、区間の指定と保存、本文の訂正、画像と経路を共有します。同じ作品・枝で保存された過去の本文、区間、関連画像も参照できます。ゲーム窓が撮影できないときに、デスクトップを代わりに撮影することはありません。

### スマホ・タブレットから接続する

スマホのブラウザーでは、利用者が PC 側に用意した非公開の転送先 URL を開きます。設定に表示される localhost URL は PC 自身の入口であり、スマホに直接入力する URL ではありません。記録Webにはユーザー認証がないため、転送先に到達できる利用者は現在の記録を閲覧・操作できます。インターネットや信頼できないネットワークには公開しないでください。

リバースプロキシを使う場合は、サイトのルートから HTTP と WebSocket を PC の `http://127.0.0.1:47832/` へ転送します。プロキシで受信可能な外部ホスト名を制限し、ブラウザー側のスキームを `X-Forwarded-Proto`、ホスト・ポートを元の `Host` または `X-Forwarded-Host` で渡します。転送ヘッダーはクライアントの値を引き継がずプロキシで上書きし、ブラウザーの `Origin` は変更しないでください。アプリ側で転送先 URL を登録する必要はありません。

## シナリオ MCP

Windows アプリの起動中に、一般の Streamable HTTP MCP client からシナリオ資料を読めます。初期状態は無効です。停止中に `scripts/configure-scenario-mcp.ps1 -DataDirectory <使用中のデータdirectoryの絶対path> -Action Enable` を実行し、アプリを起動します。接続先は既定で `http://127.0.0.1:47831/mcp`。クライアントの秘密設定へ `Authorization: Bearer <キー>` を設定します。

`StructureKey` はフロー・接続・出現位置・タグ・範囲・分類・画像一覧 metadata と区間ごとの話者名・セリフ件数、`FullKey` は本文・個別出現の話者・画像本体も取得できます。区間集計はZIPの両modeの`material.json.ranges`とMCPの共通`ranges`にあり、記録済みDialogue itemを数え、話者未確定件数を別に示します。構造キーの応答には本文・個別話者・抜粋・画像本体・thumbnail の機密 field 自体を含めず、本文/話者検索も許可しません。二権限と export で同じ対象 ID・snapshot/selection 版を使用します。`scenario_games` から作品 ID、`scenario_snapshot` から資料版と対象 ID を取得し、ID 指定や resource で参照できます。

キーは `scenario-mcp.json` に保存されます。script は秘密を表示しません。キーを prompt・コマンド履歴・共有資料へ貼らず、必要なクライアントだけへ設定してください。停止後に `-Action Rotate` で両キーを更新、`-Action Disable` で無効化し、再起動で適用します。OAuth 専用 client ではなく、Bearer header を手動設定できる client が必要です。これは API の認可であり、OS のファイル・shell・SSH 隔離ではありません。[設定・認証・各入口の契約](docs/design/scenario-mcp.md)を参照してください。

実ユーザー DB を使わない HTTP 結合 test は `dotnet test tests/GameLauncherWithGit.Mcp.Tests` で実行できます（設定 script の検証に PowerShell 7 が必要）。

枝別の記録を読む場合は、`scenario_history_scopes` で作品内の記録範囲を確認し、その `captureGameId` を `scenario_snapshot` などに渡します。従来の作品 ID は、枝の出典を持たない記録を引き続き指します。

## 配布ソースからのビルド

Release に添付する `GameLauncherWithGit-vX.Y.Z[-preview.N]-source.zip` は、本体・`library/` のサブモジュール・`native/vendor/` の MinHook と uchardet を含むソース一式です。Git管理情報と秘密鍵は含みません。GitHub 自動生成のソースZIPとは異なります。

Windows の前提環境を用意して展開先で次を実行します。ネイティブ依存は同梱ソースを使い、NuGet と .NET workload の取得にはネットワークが必要です。

```powershell
./scripts/build-luna-native.ps1
dotnet build src/GameLauncherWithGit/GameLauncherWithGit.csproj -f net9.0-windows10.0.19041.0 -c Release
```

MSIX は `scripts/publish-windows-msix.ps1` で生成できます。署名とバージョンの扱いは [Windows 配布運用](docs/design/windows-msix-keyvault-signing.md)に従い、再配布には自身の署名証明書を使用してください。
