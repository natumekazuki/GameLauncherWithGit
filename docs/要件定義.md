# 要件定義書（MVP）

## 1. 概要
Windows 11 上で、ゲームのセーブデータ等（ソースコード以外のファイル）を対象に、登録した Git リポジトリを自動で同期（fetch / pull / commit / push）する常駐アプリを作る。MVP実装は **.NET MAUI Blazor Hybrid** を採用する。

## 2. 目的
- Commit/Pull/Push の漏れを防止し、別端末でも同じ続きからゲームを再開できる状態を作る
- 「ゲーム終了後すぐシャットダウン」等の運用でも、同期漏れが起きにくい仕組みにする

## 3. スコープ

### 3.1 In Scope
- 複数リポジトリの登録・削除・一時停止
- ファイル変更検知（FileSystemWatcher）による自動同期
- 連続書き込み対策（変更が止まってから 10 秒後に同期するデバウンス）
- 同期フロー: fetch → pull --rebase → add → commit → push
- 同期状態の可視化（タスクトレイ）
- 通知（Windows Toast + タスクトレイ表示）
- ログ出力（失敗原因を追えること）
- Windows 起動時の自動起動（ユーザー操作なしで常駐開始）

### 3.2 Out of Scope
- ブランチ戦略の提供、ブランチ切り替え UI
- 競合の自動解決（競合時は停止して通知する）
- Git ホスティング（GitHub 等）の管理機能
- Git LFS の自動設定（MVPでは使わない）

## 4. 前提・制約
- 対象OS: Windows 11 専用
- 実装基盤: .NET MAUI Blazor Hybrid（.NET 8 想定）
- UI 実装: Blazor コンポーネント（Razor）で構築し、Windows 固有機能は MAUI 側のサービス経由で利用する
- 対象リポジトリは、事前に clone 済みで remote 設定済みであること
- 認証は OS / 既存 Git の認証情報（例: Git Credential Manager）を利用し、アプリが秘密情報を保持しない
- 対象は主にバイナリ（セーブデータ等）であり、差分が効かずリポジトリが肥大化し得る（容量管理は運用で対応）

## 5. 用語
- リポジトリ: ローカルの Git 作業ディレクトリ
- 監視パス: 変更検知の対象ディレクトリ（通常はリポジトリ配下）
- デバウンス: 変更が続いている間は同期を待ち、一定時間変更が止まったら同期する制御

## 6. 想定ユーザー / 利用シーン
- セーブデータを Git で管理したいが、手動コミット・プッシュを忘れがちなユーザー
- 複数PC間でセーブデータを同期して遊ぶユーザー

## 7. ユースケース
- UC-01: ゲームプレイ中にセーブが更新されたら、自動で commit/push される
- UC-02: 別端末で遊ぶ前に、ゲーム起動ランチャーで事前に fetch/pull が完了してからプレイを開始できる
- UC-03: 競合が発生したら同期を止め、通知とログでユーザーが対応できる
- UC-04: ゲームごとに関連リポジトリを紐付け、必要な分だけ事前Pullできる

## 8. 機能要件（MVP）

### 8.1 リポジトリ登録
- 複数リポジトリを登録できること
- リポジトリごとに以下を保持できること
  - ローカルパス
  - 監視パス（既定はローカルパス配下）
  - 除外パターン（MVPでは最低限。未決事項に残す）
  - 有効/無効（監視停止）

### 8.2 変更検知とデバウンス
- 監視パス配下のファイル変更を検知したら、デバウンスを開始する
- 変更が止まってから 10 秒経過したタイミングで同期処理を開始する
- 同期処理中に再度変更が発生した場合は、同期完了後に再同期を行う（過剰な連打は抑止）

### 8.3 同期処理
- リポジトリごとに以下の順で処理する
  1. `git fetch`
  2. `git pull --rebase`
  3. `git add -A`
  4. `git commit`（変更がある場合のみ）
  5. `git push`

### 8.4 競合・失敗時の扱い
- `pull --rebase` が失敗（競合）した場合
  - そのリポジトリの自動同期を停止する
  - 失敗理由（コマンド/標準出力/標準エラー）をログに残す
  - Windows 通知（Toast）とタスクトレイ表示でユーザーに知らせる

### 8.5 コミットメッセージ
- 自動コミットのメッセージは以下とする
  - `auto: save sync YYYY-MM-DD HH:mm:ss`

### 8.6 常駐・UI
- タスクトレイ常駐で動作すること
- ウインドウを閉じてもバックグラウンドで動作を継続すること
- ユーザーが明示的に「終了」した場合のみ停止すること
- 最低限の操作を提供すること（例: 今すぐ同期 / ログを開く / 設定を開く / 終了）

### 8.6.1 ゲーム起動ランチャー（プレイ前Pull）
- ゲーム実行ファイル（exe）を登録できること
- ゲームごとに「関連リポジトリ」を紐付けできること
- ユーザーがアプリからゲーム起動（ランチャー）を行うと、起動前に関連リポジトリに対して `fetch` → `pull --rebase` を実行すること
- Pull が完了するまでゲーム起動をブロックし、成功/失敗を通知すること
  - 失敗時はゲームを起動せず、ログを開ける導線を提示すること

### 8.6.2 ランチャーUI（ゲーム一覧）
- ゲーム一覧をグリッド（カード）表示できること
- 一覧の先頭（常に最前）に「＋ 新規追加」用の空カードを表示できること
  - 空カードを選択すると、ゲーム登録フローを開始する
- 各ゲームカードに紐づく操作は「詳細モーダル」に集約できること
  - カードの長押し、または右クリックで詳細モーダルを表示する
  - 詳細モーダル内に、起動 / 今すぐ同期 / 設定（編集） / 削除 / ログ などのボタンを配置できること
- 詳細モーダルを開かずに起動できる導線を用意すること
  - 各カード上に常時「▶ 起動」ボタンを表示し、タップ/クリックで即起動できること（タッチ操作を考慮）
- ゲーム登録時に以下を保持できること
  - タイトル
  - 実行ファイル（exe）のパス
  - サムネイル画像
  - 関連リポジトリ（複数）
  - 最終プレイ日時
  - ステータス（例: 未同期/同期中/同期OK/エラー）
- サムネイル画像は、ユーザーが画像ファイルを選択して登録できること
  - 入力形式は一般的な画像（例: png/jpg/webp）を受け付ける
  - 登録時に **クリッピングなし（アスペクト比維持）で縮小**し、UI表示用サムネとして保存する
    - 長辺 512px
    - 形式: PNG
  - 保存先はアプリ用ディレクトリ（`%AppData%` 配下）とする
  - 元画像は保存しない（サムネのみ保持する）
  - ゲーム登録処理はサムネイル生成が完了するまで **同期的に実行**し、完了後に登録完了とする
  - サムネイル生成に失敗した場合でも、サムネ無しで登録できること
  - 登録後にサムネイルを変更（再選択→再生成）できること
    - サムネ領域に「＋」アイコンを表示し、そこから変更できること
- サムネイル読み込み中のカードは、仮画像ではなく **スピナー（読み込み表示）** を表示する
- サムネイル未設定のカードは、デフォルトのプレースホルダー（例: 汎用アイコン）を表示する

### 8.7 通知
- 成功/失敗/停止（競合）を Windows 通知（Toast）で通知できること
- タスクトレイアイコン（状態）で、少なくとも「待機/同期中/エラー停止」が判別できること

### 8.8 ログ
- 同期実行ログを残すこと（時刻、対象リポジトリ、実行したGitコマンド、結果）
- ユーザーがログを簡単に開ける導線があること

## 9. 非機能要件（MVP）
- 信頼性: セーブ中の連続更新でコミットが乱発されない（デバウンスで抑止）
- 性能: 監視・同期がゲーム体験を著しく阻害しない（CPU/IOの過負荷を避ける）
- 運用性: 失敗時にユーザーが原因を特定できるログがある
- セキュリティ: 認証情報をアプリ内に保存しない

## 10. 受け入れ基準（例）
- AC-01: 監視対象ファイルが更新され、10秒間変更が無ければ commit/push される
- AC-02: リモートに変更があり、ローカルにも未push変更がある場合、pull --rebase を試みる
- AC-02a: ゲーム起動ランチャー経由で起動した場合、ゲーム起動前に fetch/pull が完了している
- AC-03: 競合が発生した場合、自動同期が停止し、Toast とログで通知される
- AC-04: Windows 起動時に自動起動し、タスクトレイで状態が確認できる

## 11. 運用・例外時の挙動（確定）

### 11.1 除外パターン（既定）
- 既定は **リポジトリ内の `.gitignore` を採用**する
- `.gitignore` が存在しない場合は、以下の最小セットを既定除外とする
  - `.git\`（Git管理領域）
  - `*.tmp`, `*.lock`, `~*`
- いずれの場合も、除外は **リポジトリごとに後から編集可能**とする

### 11.2 オフライン / リモート不達時
- ローカルの変更検知と commit は継続する（ローカルの履歴は残す）
- `fetch/pull/push` は失敗した場合にリトライする
  - リトライは指数バックオフ（例: 10秒→30秒→1分→…）で過剰な試行を避ける
  - 復旧したら自動的に再同期する
- 通知は「初回失敗」と「復旧時」を基本とし、連続失敗の通知は抑制する（ログには全件記録）

### 11.3 デバウンス秒数
- デバウンス秒数は **リポジトリごとに設定可能**とする
- 既定値は 10 秒

### 11.4 push 失敗時のユーザー誘導
- 原因に応じて簡易ガイドを出し分ける
  - 認証エラー: 資格情報の再サインイン（GCM等）を促す
  - ネットワーク断/リモート不達: 接続確認・復旧待ち（自動リトライ）を案内
  - 権限不足: リモートURL/権限の確認を案内
  - 競合: 自動同期停止・手動解決（rebase/abort等）を案内
- 詳細はログ（実行コマンドと標準出力/標準エラー）で確認できること
